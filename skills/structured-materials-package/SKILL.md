# 结构化内容生成多格式资料包

## 输入与输出

输入：可信内容数据、主题与标题配置、输出目录、需要生成的格式、允许交付的附件清单。输出：按科目或单元组织的资料、单独的答案册、产物清单、验证报告及可选 ZIP 包。执行文档生成时使用环境已有的 Office 技能。

此 skill 是流程说明，不附带完整生成器；可在现有生成工具上实施。不要把课程题目、机构介绍或个人路径固化进通用 skill。

## 执行流程

1. **校验内容契约**：先确认字段结构、类型、编号唯一性、题目与答案对应关系、数量和分值合计。推荐采用 JSON 等纯数据输入；动态导入 Python 内容模块会执行代码，仅限可信本地内容。记录输入摘要，避免只依赖修改时间判断变化。
2. **参数化配置**：主题、课程名称、科目目录、每单元产物种类、文件名和附件来源全部放在配置中。外部信息注明来源及核验日期，不继承过期指南中的考试事实。
3. **建立构建清单**：列出每个单元应生成的演示稿、练习卷、练习答案、测试卷和测试答案。生成前一次性创建所有输出目录，避免首次构建依赖此前运行留下的目录。
4. **同源生成**：从同一份数据派生不同格式，题目与答案按稳定 ID 对齐；正文与答案分册。内容超出版式容量时拆页或明确报错，不用截取前几项来默默丢弃材料。
5. **检查产物**：按清单逐个确认文件存在、可打开、内容对应且非空；检查题目/答案编号、公式标记残留和总分。抽检长题、表格、公式及中英混排的实际渲染。验证结果区分结构检查、内容检查与视觉检查。
6. **隔离失败**：失败单元记录到报告并使批处理返回非零状态；保留成功产物用于排查。需要完整资料包时，未全部通过不得作为完整成品发布。
7. **清单归档**：只纳入本次通过校验的产物及明确授权的附件，不对整个工作目录无差别压缩。归档相对路径不得逃出输出根目录，拒绝绝对路径、父目录跳转及指向根目录外的链接；排除凭据、缓存、旧版产物和 ZIP 本身。
8. **验证后发布**：检查源目录非空、输出文件名唯一。在目标位置附近写临时 ZIP，运行完整性测试并比对条目、数量、大小及必要的摘要；全部通过才替换旧包。失败时保留旧包，不先删除再压缩。

## 配图契约与离线交付

需要配图时，将图文映射作为构建清单的一部分，而非依赖文件名猜测位置。输入清单至少包含内容稳定 ID、题干或选项等字段、字段内顺序、唯一资源 key、本地路径、来源及允许交付范围；主题、年份、题号范围、数量和路径均由配置提供。

1. **生成前检查**：核对清单 key 唯一、内容 ID 和字段合法、资源存在且可解码；任一必需图失败则报告其映射位置并停止该单元，不以空白图或跳过图片维持成功状态。单独核对清单是否完整；仅与同一份采集清单自比，无法发现采集时已漏掉的图。
2. **按字段插入并记录**：按内容 ID、字段和顺序把图插入题干或对应选项，记录每次实际插入的 key 与位置。保存后重新打开产物，比较预期与实际记录的多重集、顺序及总数，避免只用集合比较掩盖重复项或错位。插入记录与实际文档结构分别核对；记录成功不等于文档已经嵌入正确的图。
3. **核对离线嵌入**：对 DOCX 检查实际 drawing 的图片引用、对应关系和媒体数据，确认必需图可解析且不是外链。检查范围覆盖实际使用的正文、表格、页眉等容器；媒体文件数、图片关系数与插入实例数可能因复用而不同，不强行要求三者相等。SVG 等中转格式需单独记录批次页序到资源 key 的映射，并在转换后复核；生成中转文档不等于转换成功或保真验收。
4. **检查导航与包内目标**：优先从同一份交付清单生成导航链接和 ZIP 条目路径。先解析导航中的本地链接，再按导航在包内的位置定位目标，处理 URL 编码、片段与查询部分；要求目标位于包根目录内且属于实际交付条目。外部来源链接单列，不视为离线附件。磁盘目标存在和 ZIP CRC 通过，均不能代替包内链接闭合检查。
5. **内容与视觉分层验收**：图数、嵌入关系和路径通过，只能说明结构契约；图与题意是否对应、标注是否清晰、裁剪是否缺边，仍需内容复核与实际渲染抽检。分别记录自动断言、观察指标和人工确认，不将控制台成功文案视为完整验证证据。

## 验收与汇报

- 交付清单中的必需产物齐全，输入/输出对应关系可追溯。
- 文件可打开不代表排版正确；未渲染检查时必须如实注明。
- ZIP 条目与允许清单完全一致，解压路径受控，完整性检查通过。
- 报告生成数量、失败单元、验证范围、附件来源与交付位置。

- `app/render.py:96–140,373–642,647–676`：一个块模型（标题、段落、键值、指标、表格、提示、列表、分页）同时输出 DOCX、位图 PDF 与 PNG，供打印与页面预览共用同一份内容；栅格排版在换页处重画表头（`:600–611`）。
- `app/render.py:53–75,402–423`：把上下标降级为 `^30` 一类纯文本写法。原因值得记下——Word 依赖字体自身回退，上下标字形缺失时看不见问题，PDF/PNG 由同一字体渲染才会显形，因此同一内容在不同后端暴露的问题并不一致。
- `app/render.py:647–652`：PDF 由 PIL 位图拼接生成，**没有文字层**。这意味着针对该产物的"导出内容校验"无法靠抽取文本实现，只能做结构、页数或像素层面的核对。

这次的增量只取三点：块模型单源多后端的结构、跨后端字形缺失导致"只有部分后端坏"的现象、以及位图 PDF 无文字层这一硬约束。同时须记录源实现的三处缺陷，它们正是"导出看起来成功、内容已经少了"的典型形态：单元格文本超过 3 行被静默截断（`:576,584,607`）；DOCX 表格的自动适应与显式列宽互相冲突（`:313,328–332`）；字体候选回退到默认字体后中文可能整篇为空框且无告警（`:90`）。这些属静态阅读发现，未渲染验证。
