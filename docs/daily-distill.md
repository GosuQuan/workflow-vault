# 每日沉淀 SOP

每天早上把工作区里新出现（或被改进）的、值得复用的工作流与 skill 收进本仓库。

## 1. 找增量

- 正常每日检查可用 `git -C <课程工作区> log --since=yesterday --stat`；延迟或合并执行时，从上次成功检查的时间开始，避免漏掉一天以前的变化。
- 同时检查未提交、未跟踪文件，并与已归档版本比较；提交历史不包含尚未提交的工作。修改时间只用于筛选，必要时用内容摘要确认是否变化。
- 关注三类：**可复用工具**（脚本/服务）、**可复用流程**（做法/约定）、**可复用提示词与 skill**。

## 2. 判断是否值得收

- 通用性：换个课题/课程还能用吗？硬编码的个人路径、业务数据要能参数化或删掉。
- 复用频率：一次性脚本体量小可以不收，但把它的"做法"沉淀成文档。

## 3. 脱敏与版权检查（硬性，逐条过）

- 无密钥：对候选文件 grep `api key / token / secret / password / Authorization / Bearer`。
- 无第三方版权内容：真题原文、课件截图、歌词曲谱等一律不收（工具本身可以，素材不行）。
- 无个人数据，无大二进制（PDF/图片/zip 不入库）。

## 4. 归档

- 新工具 → 新建目录 + README（用途/用法/依赖/注意），必要时把硬编码路径改成 argv 参数。
- 同类增强 → 并入现有目录，更新其 README 与根 README 的目录表。
- 纯流程/约定 → 写进 `docs/`。
- 更新根 README 的目录表。

## 5. 提交与发布

- 用 `git add -- <已审查文件列表>` 精确暂存，检查 `git diff --cached --stat` 与 `git diff --cached --check`；不要把用户的其他修改一起发布。
- 提交中文一句话信息并 push 到 `origin main`，检查退出码和分支状态；遇远程分歧先核对，不强制覆盖。
- 无合格增量时不制造空提交，汇报检查范围和跳过原因。
- 推送失败：保留本地提交，下次先核对并补推。
- 汇报本次检查截至时间、发布提交号（若有）及未解决事项，作为下次增量检查的依据。

## 6. 汇报

- 新增/更新了什么、放在哪、为什么值得收；跳过了什么、为什么。
